# General Ledger — Increment 1 Backend

Read-only general ledger evidence workspace over MaddenCo (schema `DTA273`):
chart of accounts (`GMGM`), account balances by period/year (`GMBL`), posted
audit/transaction detail (`GMAD`) left joined to actual journal entry totals
(`GTJT`) and cross-referenced against in-progress unposted journal entry
detail (`GTJD`), and a read-only listing of standard/recurring journal entry
templates (`GMSH`/`GMSD`). ETOP owns one local append-only record type: a
professional GL reconciliation note scoped to an account (and optionally a
division, department, period, and year).

This module is a data viewer, not a posting or journal-entry tool, and is
distinct from `financial_close`: it presents actual account, balance, and
transaction data as evidence, not close-cycle/control/template workflow.
It computes no automatic "in balance" verdict, close-period lock, or ERP
write. Every response is either a direct MaddenCo read or an explicit,
stated arithmetic sum/difference over that read.

## Evidence boundary

- **Chart of accounts** — `GMGM`. Search filters to `GMYNACTIVE = 'Y'` by
  default (confirmed distinct values in the live schema are `Y`, `N`, and
  blank). The primary key is the composite account number/division/
  department, so every endpoint that targets one account takes all three.
- **Balances** — `GMBL.GBAMT` ("G/L Net Balance") per account/division/
  department/period/year, returned exactly as MaddenCo recorded it. ETOP
  performs no recomputation of this value.
- **Posted transactions** — `GMAD` rows for one account/division/
  department/period/year, left joined to `GTJT` on
  `GMAD.GANBREF = GTJT.GJHNBREF AND GMAD.GAPR = GTJT.GJTPR AND GMAD.GAYR = GTJT.GJTYR`.
  This join was verified empirically against the live database before being
  relied on: `GTJT.GJHNBREF` alone repeats across different period/year
  combinations (confirmed by a duplicate-key query), so period and year are
  included in the join to avoid a false match. For manually-entered journal
  entries (`GACDSYS = 'JE'`) the join reliably surfaces the parent entry's
  total debit/credit; for entries generated by other subsystems (`AP`, `AR`,
  `TR` were observed in the live data) no `GTJT` header exists, so
  `matched_journal_entry` is `null` — this is expected, not a data gap.
- **Reconciliation check** — for the same account/division/department/
  period/year: `posted_net_total = SUM(GMAD.GAAMT WHERE GACDDBCR='DB') -
  SUM(GMAD.GAAMT WHERE GACDDBCR='CR')`, compared against `GMBL.GBAMT` as
  `difference = posted_net_total - GMBL.GBAMT`. This formula was verified
  against live rows for both a debit-normal account and a credit-normal
  account before being relied on, and matched exactly in both cases. The
  response reports the literal difference only — never an "in balance" or
  "out of balance" verdict, and never against an approved tolerance
  (no such tolerance is configured; see Gaps).
- **Unposted journal entry lines** — `GTJD` filtered to the account/
  division/department. Verified empirically that `GTJD` holds only a
  handful of rows platform-wide at any time (2 at the time of writing, out
  of 54,000+ `GTJT` header rows), because MaddenCo purges journal entry
  detail from `GTJD` once it posts to `GMAD`. This section is not, and is
  labeled as not being, a historical journal entry line archive.
- **Standard/recurring JE templates** — `GMSH` (header) and `GMSD` (lines).
  Labeled as reference templates only; a template's own debit/credit line
  totals are a stated sum of its `GMSD` lines. Templates carry no relation
  to `GMAD`/`GTJT` postings.
- **Notes** — Local SQLite, append-only (update/delete blocked by trigger),
  scoped to an account number and optionally a division, department,
  period, and year. Each note carries an evidence snapshot and SHA-256
  integrity marker over the account identity (and, when a period/year was
  supplied, that period's reconciliation check) at the time the note was
  written, following the same pattern as `vendor_intelligence` and
  `credit_risk`.

## Decisions this module does not invent

- An approved tolerance for the difference between posted-detail totals and
  the period balance — no such tolerance is configured, so the
  reconciliation check reports only the literal arithmetic difference.
- Close-period lock or reopen authority — that authority belongs to the
  `financial_close` module, not to this read-only viewer.
- An automatic "in balance" / "out of balance" verdict for any account or
  period.
- A historical archive of unposted journal entry line detail — MaddenCo's
  own `GTJD` table does not retain this once an entry posts, and this
  module does not manufacture a substitute.
